## 静态文件缓存校验、gzip 与 HEAD（2026-11-20）

- 改动：静态文件带 `ETag`（大小与修改时间）和 `Last-Modified`，未变化时返回 304；`Cache-Control` 策略不变。1 KB 以上的文本（HTML、JS、CSS、JSON、SVG）在浏览器接受时以 gzip 发送，按文件版本在内存中缓存压缩结果，压缩版本使用单独的 ETag 并带 `Vary: Accept-Encoding`。`HEAD` 与 `GET` 走同样的路由，只是不发送正文（此前返回 501）。
- 自动回归：`python3 -m unittest discover -s tests` 71 项、`node --test tests/*.test.mjs` 109 项通过，浏览器回归通过；新增用例覆盖 304（`If-None-Match` 优先于 `If-Modified-Since`、弱比较、文件改动后返回新版本）、gzip（`q=0`、小文件与二进制不压缩、压缩版本独立的 ETag）以及静态与接口的 `HEAD`。
- 无界面 Chromium（本地服务）：首次打开 47 个请求，文本均为 gzip（`app.js` 81 KB → 21 KB）；刷新后全部为 304，正文合计 491 字节。角色陪伴运行时压缩后：PixiJS 460 → 126 KB、Spine 4.1 564 → 104 KB、Spine 3.8 422 → 78 KB、Cubism Core 207 → 61 KB；`gamekee-presets.json` 169 → 17 KB。

## 碧蓝航线 Live2D 动作曲线顺序（2026-11-22）

- 现象：爱宕「盛夏进行曲」互动时出现四只手。
- 原因：Cubism 框架的 `CubismMotion` 依次读取模型、参数、部件三类曲线，每一类在遇到另一类曲线时停止。该模型除 `idle`、`touch_head` 外的反应文件都按「模型 1、参数 68、部件 2、参数 23、部件 9」交错排列，后 23 条参数与 9 条部件曲线从未生效：运行中读到 `Part28` 等本应为 0 的部件一直是 1（模型默认值），两套手臂同时显示。抽查 40 个模型，有 20 个存在交错排列的动作文件，部分连 `idle`、`effect` 也是如此（如 `pizibao_2`、`dujiaoshou_6`、`chaijun_3`）。
- 修改：载入 Live2D 时，动作文件（`.motion3.json`）按曲线类别稳定排序后再交给框架；已经有序的文件原样使用，无法解析的文件也原样使用。
- 验证：修复后爱宕在 `mail`、`touch_body`、`mission_complete` 中各部件的不透明度与文件一致（如 `Part28` 保持 0），截图只有两只手；`pizibao_2`、`chaijun_3`、`dujiaoshou_6`、`aidang_2` 的立绘与互动均正常就绪、无页面错误。`node --test tests/*.test.mjs` 124 项（新增曲线排序：类别有序、同类保持原顺序、不改动原文件、已有序原样返回、未知类别放最后）、`python3 -m unittest discover -s tests` 89 项与浏览器回归通过。
